# Security

## Supported versions

The latest release and `main` between releases. Fixes land on `main` and ship in the next release; no release is patched. v1.5.0 is the last release that runs on Neovim 0.8 and 0.9 and receives no fixes; `main` and every release after v1.5.0 need Neovim 0.10.

## Reporting a vulnerability

Use GitHub's private vulnerability reporting: <https://github.com/selimacerbas/live-server.nvim/security/advisories/new>. Do not open a public issue for a security problem.

You get a reply within seven days. A confirmed report is fixed in a release and credited in the advisory unless you ask otherwise.

## What the server exposes

live-server serves the directory you point it at, on `127.0.0.1` by default, and `token` is the boundary.

Who can reach it. The loopback bind keeps other machines out, and its Host check answers 421 to a request under any name but `localhost`, a `*.localhost` name, a loopback address or a name `allowed_hosts` lists, which keeps out a page that reaches the port through DNS rebinding; `allowed_hosts = true` turns the check off, and a bind to any other address, `0.0.0.0` included, has none. A name `allowed_hosts` lists is trusted as far as its DNS: whoever controls that name's records can point it at this machine and read the server from their own page. Neither keeps out a page that addresses a loopback address itself: any page can send the server requests. No bind keeps out another program on this machine, which can read every file the server answers without the token. The server speaks plain HTTP with no TLS, so on a network bind the token and every answer cross the network readable.

Who can read its answers. With the Host check on (a loopback bind without `allowed_hosts = true`), a page on another site reaches the server only as another origin, unless its name is one `allowed_hosts` lists and that name points at this machine, which makes the page the server's own origin; for every other page `cors` governs what it reads: with `cors = true` or `"*"` any page can read the root route's answers, and with a list or one origin the pages it names can; no `/__live/` route carries an `Access-Control-Allow-Origin` header, so no such page reads the event stream's or the asset route's. Another `Access-Control-` header you set in `headers` reaches the files and listings the root route serves, the event stream and the asset route, and not the injected client, the inject endpoint, the `cors` preflight's answer, which carries its own Access-Control fields alone, or any error answer; it opens no read without that origin line. With `cors = false`, an `Access-Control-Allow-Origin` you set in `headers` is still sent on the root route, so a `"*"` there lets every site read it. With the check off (a network bind, or `allowed_hosts = true`), a page whose name rebinds to this machine is the server's own origin and needs no CORS header: it reads the root route, and without the token the event stream and the asset route too, so a network bind needs `token`, and `protected_paths` for every file that must stay private.

What the root route serves. Every file under the root, but a dot path unless `serve_dotfiles` is set (`/.well-known/` at the root is served either way) and an entry named `__live` at the root, in any letter case, file or directory, or a link of that name to anything, which it does not serve, nor any file in it, whatever the spelling of the request's first segment, nor a file a link elsewhere in the root resolves into it, for any method, a `cors` preflight included, which gets a 404 and no origin line (a hard link elsewhere in the root to a file in it is a separate name, which it serves); and the file you started on, which is served at `/` and by its own name when that name is served (a plain file, or a dot file with `serve_dotfiles`), and at `/` alone even when it is a dot file (a `.draft.html`) or sits in that directory; with `host = "0.0.0.0"` all of it is reachable by anyone who can reach the port, as the README's Design notes say. With `auto_start`, the root follows the files you open: opening a matching file in another folder moves the root of the server running on `auto_start`'s port there, with no notice under `notify = false`, so on a network bind every such folder becomes readable in turn. The directory listing, on by default, names every file and directory the dot rule leaves visible, the `__live` entry excepted, to anyone who can reach the port, the files `protected_paths` gates included. The event stream names files too: every reload frame carries the changed file's path under the root, which on a server without `token` anyone who can reach the port reads. Where a file's name is itself a secret, turn the listing off (`directory_listing.enabled = false`) or gate the directory that holds it with `protected_paths`, and set `token`, which gates the stream. An HTML or SVG document the root route serves runs its script in the server's origin, where it can read the token the injected client keeps in `sessionStorage` and request every gated path with it, so serve only documents you trust.

What the asset route serves. `/__live/asset`, which a plugin turns on with `asset_root`, serves any regular file under `asset_root`, which may lie outside the root, dot files included, and a `__live` directory too: the dot rule and `serve_dotfiles` do not apply there. It refuses a list of names (credential files such as `.env` and `id_rsa`, key and certificate files by extension, paths through `.git`, `.ssh`, `.aws` and the like), and that list is no guarantee: a secret under another name is served. It sends an HTML, SVG or XML file with a `sandbox` directive in `Content-Security-Policy`, so a document there runs no script in the server's origin.

The token. With no `token`, the event stream and the asset route answer anyone who can reach the port; the inject endpoint refuses a browser request from another site and answers the rest: on a loopback bind any program on this machine, and a page served under a name `allowed_hosts` lists (any name, with `allowed_hosts = true`) that reaches the server over HTTPS (a tunnel or a TLS proxy in front of it), whose request the browser then marks as same-origin, so that page fires events at every open page; over plain HTTP a browser sends that name no such mark, and the request, unmarked under a name that is no loopback name, is refused (403); on a network bind any peer that sends a browser's same-origin mark. So `token` is the boundary against a peer that is not a browser and against a page under such a name; with one, they and the paths `protected_paths` names require it, the injected client `/__live/script.js` excepted, and every other file the root route serves, `/.well-known/` at the root among them, stays readable. A `protected_paths` pattern matches the request path and the file's path under the root as the disk spells its name: on a case-insensitive file system, a pattern cased otherwise than the name on disk leaves the file readable without the token, and a hard link to a protected file under another name is not gated. A request without the token is matched against every pattern on the editor's own loop. `start` refuses the costliest pattern shapes and the 8 KiB cap on a request target bounds the path, as the README states below its start-key table, but what is left is a stated limit, not a bound: with the costliest pattern found, one read of an 8 KiB path costs at most about 105 ms of CPU time per pattern (about half that on a quiet machine), and a request reads a pattern on each name it reaches, as the README counts them: any target ending in `/`, a directory there or not, reads a pattern holding a frontier (`%f`) whose set treats `/` and the path's end differently twice, at most about 170 ms, and a directory request reads such a pattern up to five times (a link or another letter case asked with its slash), on names the OS's path limit holds to 4 KiB on Linux, up to about two and a half times the 8 KiB figure; `^/.*%.md$` costs about 0.1 ms (measured on an Apple M2 laptop). The cost adds up over the patterns and over concurrent requests, so whoever sends many such requests holds the editor's loop for their sum: on a loopback bind that is not only a peer but any web page open in the browser, which can address the port (above) with requests no check before the patterns refuses, an image's among them; a request carrying the token runs no pattern. Keep the list short and its patterns anchored. The token also travels beyond the server: the start notice prints the URL that carries it, which `:messages` keeps, unless `notify = false`; the browser is opened with that URL as a command argument, which other accounts on this machine can list; the browser keeps the URL in its history; and every response carries `Referrer-Policy: strict-origin` (or `no-referrer`, when you set that in `headers`), so a Referer names the server's origin at most, which a page's own `<meta name="referrer">` can widen to the whole URL, token included.

Connections. `max_connections` (64 by default) is one pool for every peer, and a connection holds its place until its socket closes: `header_timeout_ms` (10 seconds by default) frees one whose request head never arrives, but a response a peer reads slowly and an event stream hold theirs for as long as the peer keeps them open, so anyone who can reach the port can hold every place without the token and keep a token holder out. A plugin sets the two through `server.start`; `setup()` refuses both keys, so every server the commands or `auto_start` open runs with the defaults.

The start probe. On a wildcard bind, `start` refuses when another socket holds the loopback address its own URL names; it checks that address once, at start, and no other, so a program that binds it later takes the requests sent to the URL, token included, and a URL another plugin builds on another address (a LAN address on a `0.0.0.0` bind) is not covered.

A known limit: the server checks a path, then opens it, two separate lookups. A process that can write the served tree (or `asset_root`) can swap a file for a link between the check and the open, and the server then sends the link's target, which may lie outside the root, on a dot path or under a protected name. Serve a tree only accounts you trust can write. A string `asset_root` is resolved again on every asset request and must still name the real path kept at start, so a link given as `asset_root` and pointed elsewhere after start, or a link put at its path, is refused (404 and a warning); a directory put at that same path, or a tree rebuilt at any directory above it, is served, so a process that can write any directory above `asset_root` can change what the asset route serves between the start and a request. The root route checks nothing of the kind: a directory put at the root's path after start is served without a word, so a process that can write any directory above the root can change what the root route serves.

A report that shows a way around the token gate or the path containment, a name the loopback Host check admits that this machine does not answer to, or a page on another site that fires events, is in scope.
